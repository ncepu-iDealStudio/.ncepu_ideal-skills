# 开源 SDD（规格驱动开发）工具对比与选型

> 本文对比与 GitHub [Spec-Kit](https://github.com/github/spec-kit) 同类的开源 SDD 项目。
> SDD（Spec-Driven Development，规格驱动开发）的核心范式是：**先产出可纳入 Git 版本管理的 Markdown 规格文档（spec / plan / tasks），再动手写代码**，以此对抗 vibe coding（氛围编程）。

---

## 1. 背景与范围

### 1.1 筛选标准

- 开源项目
- 遵循 SDD 范式
- Star 数尽量接近或高于 Spec-Kit（约 130k），且真实用户量大
- 支持 Cursor / Claude Code / DSH（DeepSeek-Harness）

> Star 数据为 2026-09 快照，仅用于量级参考。

### 1.2 概念区分

- ✅ **SDD 工具**：专门做「spec 文档 → 方案 → 任务 → 编码」流水线（见本文对比表）
- ❌ **普通 AI Agent**：Cline、RooCode、OpenCode、Aider 等只负责执行代码，**不属于**规格驱动框架，不在对比范围内

## 2. 主流项目对比

### 2.1 项目概览

| 项目 | 仓库 | Star（2026-09） | License | 核心定位 |
| --- | --- | --- | --- | --- |
| **Spec-Kit** | `github/spec-kit` | 130k+ | MIT | GitHub 官方；绿场新项目优先；线性流水线：constitution → spec → clarify → plan → tasks → implement；preset / extension 扩展生态强大 |
| **OpenSpec** | `0mega/OpenSpec` | ~68k | MIT | 主打存量老项目（Brownfield）；delta-spec 变更提案模式，每个改动独立文件夹存放 proposal / spec / plan / tasks |
| **Task-Master-AI** | `eyereasoner/Task-Master-AI` | ~28k | MIT-Commons-Clause | PRD 输入 → 自动拆解为有序 `tasks.json`；重点做任务分解，完整 spec 生命周期较弱 |
| **BMAD-METHOD** | `bmad-code-org/BMAD-METHOD` | ~53k | MIT | 大型复杂特性；多 Agent 协作；完整 PRD + 架构 + 风险 + 合规；适合企业复杂业务系统 |
| **SpecD** | `specd-sdd/SpecD` | ~12k | MIT | 工程团队向；spec 与源码符号、依赖关联，可计算变更影响；MCP 服务，校验 spec 与代码一致性 |
| **Kiro-Specs** | `aws/kiro-specs` | ~31k | MIT | AWS 开源；EARS 结构化需求语法，形式化程度高；适合嵌入式、安全合规项目 |

### 2.2 差异与适配

| 项目 | 与 Spec-Kit 的差异 | 支持 Agent | DSH / WorkBuddy 适配 |
| --- | --- | --- | --- |
| **Spec-Kit** | 绿场（从零新建系统）最强；重 constitution 宪章；扩展生态最繁荣；对存量老项目较弱 | Cursor、Claude Code、DSH、Aider、Windsurf、Copilot CLI | ✅ DSH 完整原生支持；❌ WorkBuddy 无法完整运行，只能手工提取单文件 skill |
| **OpenSpec** | Spec-Kit 偏新项目，OpenSpec 擅长在已有代码库迭代功能；不强调宪章；支持变更归档；命令 `/opsx:*` | 20+ Agent，含 DSH、Cursor、Claude Code | ✅ DSH 原生支持；❌ WorkBuddy 不支持整套，只能提取单片段 |
| **Task-Master-AI** | 没有完整 spec→plan 全链路；强项是把现成 PRD / md 拆成分层、带依赖的任务列表；不做 constitution 与需求澄清；输出以 JSON 而非 md 为主 | Cursor 最佳，支持 Claude Code、DSH、Windsurf | ✅ DSH 可用；❌ WorkBuddy 不支持多文件 / JSON 产物，适合作为 Spec-Kit 下游工具 |
| **BMAD-METHOD** | 流程更重；内置风险评估、安全审计、多角色分工；适合大型业务，小项目显得过重 | Cursor、Claude Code、DSH | ✅ DSH；❌ WorkBuddy 无法运行整套多文件 skill |
| **SpecD** | LLM 仅作辅助；大量校验逻辑写在代码而非 prompt；可检测 spec 与代码不一致；重工程校验 | DSH、Cursor、Claude Code | ✅ DSH（MCP 模式）；❌ WorkBuddy 完全不支持 MCP |
| **Kiro-Specs** | 需求语法偏严谨工程形式化，spec 编写成本更高；更适合高合规要求；绿场为主 | Cursor、Claude Code | ✅ DSH 可部署；❌ WorkBuddy 不支持 |

## 3. 重点项目深度解读

挑选最值得评估的三个项目：**OpenSpec / Task-Master-AI / BMAD-METHOD**。

### 3.1 OpenSpec —— 最值得与 Spec-Kit 对比

> `0mega/OpenSpec` · ⭐68k

1. **核心哲学：面向存量代码库迭代**
   - Spec-Kit 非常适合从零起新项目，在老项目上会比较笨重
   - OpenSpec 面向已有项目新增 / 修改功能：每个变更建立独立目录 `proposal/`、`spec/`、`plan/`、`tasks/`，每个 feature 改动作为一份提案，可归档、回滚、对比
2. **命令前缀**：`/opsx:new`、`/opsx:propose`、`/opsx:apply`、`/opsx:archive`
3. **不强制 constitution 宪章**；可导入外部 PRD 文档作为输入
4. **与现有链路结合**
   - 老系统迭代：优先 OpenSpec
   - 全新系统立项：优先 Spec-Kit
5. **兼容 DSH**，安装：`openspec init --integration dsh`

### 3.2 Task-Master-AI —— PRD → 任务拆解引擎

> `eyereasoner/Task-Master-AI` · ⭐28k

1. 定位不是完整 SDD 全栈，而是**【PRD → 任务拆解引擎】**
2. 输入：任意 PRD / `spec.md`；输出：结构化 `tasks.json`，分层、标记依赖、并行任务、文件修改路径
3. 没有需求澄清、没有 plan 架构设计；适合作为 Spec-Kit / OpenSpec 的下游——spec 写完后丢给 Task-Master 输出任务清单
4. 适合场景：已有成熟需求文档，只想要可靠的任务拆分

### 3.3 BMAD-METHOD —— 企业大型业务功能

> `bmad-code-org/BMAD-METHOD` · ⭐53k

1. 面向企业大型业务功能；流程很重：业务调研 → PRD → 风险分析 → 架构方案 → 多轮评审 → 任务分解
2. 内置安全审计、合规检查；适合 IT 招投标、企业业务系统
3. 代价：小功能开发仪式感太强，效率低

## 4. 选型决策建议

结合技术栈：**DSH + WorkBuddy + superpowers**。

| 场景 | 首选工具 |
| --- | --- |
| 新建绿场项目（0→1 系统） | **Spec-Kit** |
| 已有老项目迭代新功能 | **OpenSpec** |
| 只需要把现成 PRD 拆成任务 | **Task-Master-AI**（可配合 Spec-Kit 使用） |
| 大型企业级、强合规与风险评估 | **BMAD-METHOD** |
| 需要严格校验 spec 与代码一致性、工程校验 | **SpecD** |

> ⚠️ **WorkBuddy 限制**：上面所有完整 SDD 框架都无法在 WorkBuddy 中完整运行。WorkBuddy 只能跑单文件 `SKILL.md`；完整 SDD 框架依赖 CLI、多目录、多文件产物、MCP、扩展系统，只能运行于 **DeepSeek-Harness（DSH）/ Cursor / Claude Code**。
>
> 可行组合：**WorkBuddy 做简单 prompt 增强；复杂 SDD 工作流全部交给 DSH 执行**。

## 5. 工作流组合示例

**环境**：DSH。工具链：Spec-Kit + Task-Master-AI + superpowers + HTML 原型 skill。

```text
/speckit.specify + /speckit.clarify → specs/spec.md
→ 调用 md-prd-to-html-prototype skill 生成 HTML 原型
→ /speckit.plan → specs/plan.md
→ Task-Master 解析 spec + plan 输出 tasks.json
→ superpowers 执行 TDD 编码实现
```
