# 端识别、澄清与状态文件契约（intake-and-state）

本文件只规定生成前如何问用户、缺信息如何处理，以及状态文件的内容模板。
目录与命名见 `output-contract.md`；离线 HTML 与交互实现见 `interaction-contract.md`。

## 1. 步骤 1：确认输入与解析

- 必须向用户询问并确认两项输入：①本地 MD 需求文档路径；②原型根目录路径。两项都明确后才继续。
- 读取 MD 全文，解析并记录以下信息：系统名称、一句话定位、目标角色、页面清单、每个页面的字段（输入框/下拉/日期/表格列/按钮）、按钮与弹窗、表格列、筛选条件、交互行为（新增/编辑/删除/查询/状态切换）、非功能约束（是否移动端优先、后台还是 C 端）。
- 解析结果作为后续选端、模式选择、数据字典与 Mock 数据的唯一事实来源，不凭空补充 MD 中不存在的内容。
- 非功能约束中若明确要求移动端优先或存在 C 端门户，应在步骤 2 的候选端建议中体现。

## 2. `[NEEDS CLARIFICATION]` 澄清标记

- 当页面清单、关键字段或必要交互信息缺失、含糊或自相矛盾时，不得猜测、不得编造字段。
- 输出待确认清单，逐条使用统一格式：`[NEEDS CLARIFICATION: <具体问题>]`，例如 `[NEEDS CLARIFICATION: 订单列表是否需要按创建时间区间筛选？]`。
- 每条问题只问一个具体点，指向 MD 中缺失或冲突的位置；一次性列全，避免多轮零碎追问。
- 输出清单后立即停止：不进入选端、不写状态文件、不生成任何 HTML，直到用户补充信息。
- 已确认的信息保留，用户补充后从未澄清处继续，不重复询问已回答的问题。

## 3. 步骤 2：候选端识别（每次必问）

- 基于角色与页面，判断 `www`、`admin`、`app` 中哪些与该系统相关，形成候选端列表并简要说明依据。
- 让用户勾选需要生成的端，并明确指定"本次先生成哪个端"；每次调用只生成一个端。
- 即使 `_原型说明.md` 已记录候选端或已生成端，也必须以本次对话的用户回答为准重新确认，不得用状态文件跳过提问。
- 状态文件中的历史只用于复用既有分析结论（如页面归属、数据约定），不替代本次选端确认。
- 用户未勾选任何端或未指定本次生成哪个端时，不进入步骤 3，先补齐确认。

## 4. 步骤 3：模式选择（每次必问）

- 让用户二选一：单页原型或多静态页原型；即使状态文件记录了上次模式也要重新询问。
- 解释差异：单页＝一个 HTML 内含全部视图、菜单切换；多静态页＝每页一个 HTML、真实 `href` 跳转、另有 `index.html` 导航入口。
- 将用户选择记为 `single` 或 `multi`，供生成与校验使用（目录形态见 `output-contract.md`）。
- 模式只对本次选中的端生效；其它端日后生成时可另选模式，互不影响。

## 5. 状态文件内容模板（七小节骨架）

新建 `_原型说明.md` 时使用以下骨架；尖括号字段按解析结果填写，模板中的示例仅示意格式：

```markdown
# <系统名称> 原型说明

## 1. 系统名称与一句话定位
<系统名称>：<一句话说明系统做什么、服务谁>

## 2. 目标角色清单
- <角色A>：<职责简述>
- <角色B>：<职责简述>

## 3. 候选端与已生成端
- 候选端：www / admin / app（依据：<角色与页面判断依据>）
- 已生成端：<端名>（生成时间：<YYYY-MM-DD HH:MM>）

## 4. 页面清单（按端分组，标注模式）
- www（模式：single|multi）：<页面1>、<页面2>
- admin（模式：single|multi）：<页面3>
- app（模式：single|multi）：<页面4>

## 5. 数据字典与 Mock 数据约定
| 实体 | 字段 | 类型 | 示例值 | 状态枚举 |
| --- | --- | --- | --- | --- |
| <实体> | <字段> | <类型> | <示例值> | <枚举值列表> |
Mock 命名约定：const MOCK_<实体名复数> = [...]

## 6. 待确认业务点
- [NEEDS CLARIFICATION: <具体问题>]

## 7. 生成历史
- <YYYY-MM-DD HH:MM> | 端：<www/admin/app> | 模式：<single/multi> | 产出：<文件清单>
```

## 6. 读写与续写衔接

- 生成前先读取 `_原型说明.md`：存在则在原文件上续写，不存在则按第 5 节模板新建（文件位置与命名见 `output-contract.md`）。
- 续写只更新本次涉及的端与小节；"生成历史"追加、不覆盖；七个小节必须始终齐全。
- 第 2、3 节的确认不再依赖状态文件：每次调用都重新问端与模式，状态文件仅提供上下文。
- 第 6 节汇总所有仍未解决的 `[NEEDS CLARIFICATION]`；已被用户补充确认的问题从中移除。
