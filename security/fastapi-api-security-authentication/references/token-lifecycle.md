# 会话与令牌生命周期（通用）

本文件不绑定任何具体表名或字段名。目标是把「登录签发一个 access token」升级为**可撤销、可续期、可重置**的完整鉴权体系，并给出统一的完整性判定，避免把半套实现报告为已完成。

## 一、为什么只有访问令牌不够

无状态 JWT 只能证明「签名有效、未过期」，不能证明：

- 会话是否已被登出、被管理员强制下线或已过期；
- 刷新令牌是否被轮换、是否被重复使用；
- 账号被禁用/锁定/删除后，旧令牌是否应立即失效；
- 用户改密或走完密码重置后，旧会话是否失效；
- 密码重置链接是否已被使用过、是否过期。

因此：**数据模型或需求中出现会话、刷新令牌、吊销、过期、重置令牌等结构时，只做签名校验而宣称「鉴权完成」属于错误结论**。必须实现对应生命周期，或明确标注「鉴权体系不完整（缺刷新/吊销/重置）」并说明影响。

## 二、完整性分级（按数据模型与需求判定）

| 级别 | 能力 | 适用信号 |
| --- | --- | --- |
| L1 仅令牌 | 签名 + 过期校验，无服务端会话 | 无会话表、无注销/多设备/重置需求 |
| L2 会话型 | 服务端会话记录 + 刷新令牌轮换 + 登出/吊销 + 绝对/空闲过期 + 账号状态实时校验 | 存在会话/刷新记录、设备维度、吊销时间、过期时间等结构 |
| L3 可恢复账户 | L2 + 改密/重置后吊销全部会话 + 重置令牌一次性消费（摘要存储、过期、已用标记） | 存在密码重置令牌结构，或需求包含找回/重置密码 |

判定顺序：

1. 先看**数据模型**（字段语义，不看表名）；
2. 再看**需求/接口说明**是否要求多设备、登出、强制下线、刷新、找回密码；
3. 取两者要求的最高级别作为本轮应实现的级别；
4. 实现不了时降级必须写进报告与权限说明，不能默认当作已完成。

## 三、结构识别（字段名不固定）

按语义识别，命名可能完全不同；以下只是常见写法。

| 概念 | 常见字段/结构线索 | 用途 |
| --- | --- | --- |
| 会话/刷新记录 | `session`、`refresh_token`、`refresh_token_hash`、`token_digest`、`revoked_at`、`revoked`、`expires_at`、`idle_expires_at`、`last_active`、`device`、`jti`、`token_version` | 多设备、续期、吊销、超时 |
| 重置/验证令牌 | `reset_token`、`verification_token`、`otp`、`token_hash`、`used_at`、`consumed_at`、`expires_at`、`status` | 一次性改密/验证 |
| Cookie 传输 | `set_cookie`、`HttpOnly`、`SameSite`、`secure=`、`Cookie(...)` | 浏览器端令牌携带 |
| 生命周期接口 | 路径含 `refresh`、`logout`、`sign-out`、`revoke`、`password/reset`、`forgot` | 刷新、登出、重置 |
| 生命周期方法 | `refresh`、`rotate`、`logout`、`revoke`、`reset_password`、`forgot_password` | Service 层能力 |

预检脚本会把上述线索汇总到 `token_lifecycle` 字段（只列证据，判定仍按本节规则）。

## 四、令牌与 Cookie 设计

### 访问令牌

- 短生命周期（建议 5–30 分钟），只放 `sub`、`jti`、`exp`/`iat` 等最小声明。
- 角色/权限每次请求按服务端数据加载；不要把长期授权写死在令牌里。
- 通过 `Authorization: Bearer` 或 HttpOnly Cookie 携带；不要放在 URL 查询参数。

### 刷新令牌

- 高熵随机串（非 JWT 亦可），**数据库只存摘要**（如 SHA-256），不存明文。
- 绑定到会话记录与账号；记录签发/轮换时间、过期时间、设备信息。
- **轮换**：每次刷新签发新刷新令牌并标记旧令牌失效；发现旧令牌被重复使用 → 判定为窃取，吊销该会话（reuse detection）。
- 绝对过期 + 可选空闲过期；过期后刷新返回 401。

### Cookie 传输（浏览器场景默认）

先确定传输模式，并写进权限说明：

| 模式 | 适用 | 刷新令牌位置 |
| --- | --- | --- |
| Cookie 模式（浏览器默认） | 有前端页面、需要会话续期与登出 | **HttpOnly Cookie**，响应体不返回刷新令牌 |
| Bearer-only 模式 | 纯 API、移动端或用户明确要求 | 客户端自行保存；此模式必须在文档中声明不支持浏览器登出/吊销语义 |

需求出现「刷新令牌」「会话」「Cookie」等描述时，按 Cookie 模式实现；不要默认把刷新令牌塞进 JSON 响应体。

#### 1. 登录响应

- `Set-Cookie` 写入刷新令牌；响应体只返回 access token、有效期与用户信息。
- 响应 Schema **不得包含 `refresh_token` 字段**（Cookie 模式下即使保留字段也必须为空，最简做法是直接不定义）。
- Cookie 属性：

| 属性 | 要求 |
| --- | --- |
| 名称 | 可配置（如 `refresh_token`），不要与 access token 混用 |
| `HttpOnly` | 必须开启，禁止 JS 读取 |
| `Secure` | 生产必须开启；开发/测试可按环境关闭 |
| `SameSite` | `Lax` 或 `Strict`；跨站前端需评估 `None` + CSRF |
| `Path` | 限定到认证前缀（如 `/api/v1/auth`），不要 `/`，避免随业务请求发送 |
| `Max-Age` / `Expires` | 与刷新令牌绝对过期一致；轮换后重设 |
| `Domain` | 最小化，不写泛域名 |

- 刷新令牌明文不进入响应体、URL、日志、审计详情。

#### 2. 刷新接口契约

- `POST /auth/refresh`（或等价路径）**不接收刷新令牌请求体**；令牌从 Cookie 读取。
- 参数只保留非敏感信息；身份、设备、用户 ID 一律不从 body 信任。
- 缺失/无效/过期/已轮换 Cookie → 401，统一文案。
- 轮换成功后：`Set-Cookie` 写入新刷新令牌（沿用同样属性），响应体返回新 access token；旧刷新令牌立即失效。
- 不要同时「Cookie 与 body 都读」；确需兼容期时 Cookie 优先，并在文档写明退出时间。

#### 3. 登出与吊销

- `POST /auth/logout` 用 access token 定位当前会话并吊销，同时 `Set-Cookie` 清空刷新 Cookie（`Max-Age=0` / 过期时间置前）。
- 管理员强制下线/改密/重置后，客户端刷新 Cookie 自然失效；服务端不得依赖客户端清理。

#### 4. 设备名称来自请求头

- 设备名称只用于展示与审计，**从请求头获取**：优先可信的 `X-Device-Name`（若网关写入），否则 `User-Agent`；为空回退 `unknown`。
- 不允许从请求体接收 `device_name`，也不要作为身份或权限依据；body Schema 应 `extra="forbid"` 拒绝该字段。
- 截断到列长度（如 100），避免超长头写入失败；不要把整个 User-Agent 原样记入日志。

#### 5. CSRF 与 OpenAPI

- Cookie 模式必须考虑 CSRF：SameSite 之外，对刷新/登出等状态变更请求增加 CSRF token 或等价双提交校验。
- OpenAPI 中刷新/登出应声明 Cookie 安全方案（如 `APIKeyCookie`），登录响应注明 `Set-Cookie`，避免文档让人误以为刷新令牌走 body。

实现样例见[Cookie 认证模板](templates/cookie-auth.md)。


### 服务端校验

- 至少在每个受保护请求或刷新时检查：会话存在、状态可用、未绝对过期、未空闲超时、未吊销。
- 账号状态/角色变更实时生效（禁用/锁定/删除 → 401）。
- 401 与 403 的语义、业务码、文案沿用既有策略，不得用 404 掩盖未认证。

## 五、生命周期动作

| 动作 | 必须做的事 |
| --- | --- |
| 登录 | 校验口令 → 创建会话 → 签发 access + refresh（refresh 只存摘要） |
| 刷新 | 校验 refresh 摘要/状态/过期 → 轮换 → 旧 refresh 立即失效 |
| 登出 | 吊销当前会话；响应清除 Cookie；access/refresh 均不可再用 |
| 强制下线 | 管理员按账号吊销会话；被吊销会话的 access/refresh 立即 401 |
| 改密 | 校验旧口令 → 更新哈希 → 吊销该账号全部会话 |
| 密码重置 | 申请：不泄露账号存在、高熵令牌、存摘要+过期+状态；使用：事务内校验并标记已用 → 改密 → 吊销全部会话 |
| 重置令牌 | 一次性：已用/过期/状态不符一律拒绝；失败文案统一 |

## 六、判定与停问

出现以下任一情况且用户未声明「本轮不做会话/重置」时，按缺失处理：

- 数据模型存在会话/刷新/吊销/过期/重置相关字段，但代码只有登录与访问令牌；
- 需求包含多设备、登出、强制下线、刷新、找回/重置密码；
- 代码里 `verify_token` 只验签，从不查询会话状态，却对外宣称支持注销。

停问话术：

```text
检查结果：数据模型/需求包含会话或刷新令牌、密码重置相关结构（列出识别到的表与字段），
但现有实现只签发了访问令牌，缺少刷新轮换、登出/吊销、以及密码重置令牌的一次性消费与旧会话失效。
按该模型，鉴权体系应达到 L2/L3；只做签名校验会无法安全续期、无法强制下线、重置链接可重复使用。
是否需要我补齐会话/刷新令牌生命周期与密码重置流程？请回复「是」或「否」。
若否，本轮只能按 L1 交付，并在报告与权限说明中标注「鉴权体系不完整」。
```

用户同意：按 L2/L3 实现并补测试；用户拒绝：**不得宣称完成**，必须在交付报告与权限说明中写明未实现的级别与风险。

## 七、测试矩阵（按实现级别取用）

| 情形 | 断言 |
| --- | --- |
| 登录 | access 可访问；Cookie 模式下响应体**不含**刷新令牌，`Set-Cookie` 含 HttpOnly / SameSite / Path / Max-Age，生产含 Secure |
| 刷新轮换 | 只带 Cookie 即可刷新；旧 refresh 再用必须 401；响应 `Set-Cookie` 为新值 |
| 刷新接口契约 | 只传 body、不带 Cookie → 401/422；不接受 body 中的 refresh_token 或 device_name |
| 拒绝 body 凭证 | body 带 `refresh_token` 时 `extra="forbid"` 返回 422（或明确忽略但不得生效） |
| 刷新重放 | 连续重放旧 refresh → 401，且原会话被吊销（后续 access 也 401） |
| 登出 | 当前 access 与 refresh 均失效；响应清空刷新 Cookie |
| 设备名称 | 用 `User-Agent` / 可信 `X-Device-Name` 登录后，会话记录的设备名来自请求头；body 传 `device_name` 返回 422 或不生效 |
| 强制下线 | 管理员吊销后，目标用户 access/refresh 立即 401 |
| 绝对/空闲过期 | 过期后 refresh/access 均 401 |
| 账号禁用/锁定 | 已有 access 立即 401 |
| 改密 | 旧 access/refresh 立即 401；新口令可登录 |
| 重置令牌 | 首次成功；重复使用 401/400；过期 401/400；摘要不符拒绝 |
| 重置成功 | 该账号全部旧会话失效 |
| Cookie 安全 | HttpOnly、Secure（生产）、SameSite、Path 与 CSRF 校验存在 |
| 敏感输出 | 响应、日志、URL 不含 refresh 明文、重置令牌明文、哈希 |

不允许用「登录成功」「路由清单」「全员 403」替代上述生命周期断言。

## 八、反模式

- 只验签不查会话，却声明支持登出/强制下线；
- 刷新令牌明文入库或写入日志；
- 刷新令牌永不过期，或轮换后旧令牌仍可用；
- 重置令牌可重复使用、无过期、无摘要存储；
- 改密/重置后旧会话继续可用；
- Cookie 无 HttpOnly/SameSite，或把令牌放进 URL；
- **登录把刷新令牌放进 JSON 响应体，却声称使用 Cookie 会话**；
- **刷新接口从请求体读刷新令牌，Cookie 形同虚设**；
- **设备名称从请求体读取或允许客户端改写归属**；
- 会话/重置表已存在但长期为空，仍宣称鉴权体系完整。
