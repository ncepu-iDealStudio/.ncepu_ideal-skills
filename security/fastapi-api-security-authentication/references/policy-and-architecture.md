# 认证与授权设计

目标是加固现有 API，防止未授权访问、水平越权和垂直越权；保留原脚手架的 Resource → Service → Repository → Model 分层。原脚手架 Skill 只读。

## 一、确定实际规则

1. 读取项目现有路由、SQL/模型、账号和角色、Service 与测试，列出实际 HTTP 方法、路径、用途、对应角色、对象归属和规则依据。与实际注册路由交叉核对，包括隐藏接口和非 `*Resource.py` 文件中的路由，不能只看 OpenAPI 或文件命名。
2. 用户未提供业务规则也继续执行：按[权限推断与默认策略](default-policy.md)结合现有证据设计角色、对象和字段范围；说明规则来自用户、证据推断还是默认选择。不能将字段名或示例记录单独当成真实归属，也不能因缺少规则说明而对全部角色关闭普通业务。无法安全确认身份或建立对象关系时，限制相关普通用户访问并说明阻碍。
3. 白名单逐项明确 HTTP 方法和路径，例如约定的登录入口；其他业务路由默认受保护。健康、文档、HEAD、OPTIONS/CORS 按实际部署和框架行为分别确认。禁止仅靠前缀、模糊匹配或忽略方法放行；规则缺失或检查失败不得默认允许。

## 二、代码位置与执行

- 沿用脚手架已有的 `middleware/`（不是凭猜测新建相近目录），在其中组织白名单、令牌认证、角色/对象权限判断和供接口使用的**鉴权装饰器**。在应用工厂或现有装配位置接入请求认证；登录等公开入口应有明确公开标记或白名单规则，不能对其施加必须登录的检查。
- 每个受保护接口明确使用该目录定义的鉴权装饰器，检查经过认证的主体及该操作允许的角色；不能仅因为有 `@router.get` 或普通异常装饰器就认为完成。非白名单业务路由漏挂装饰器时，应在启动核对阶段报错，或在请求执行前拒绝，不能只验 JWT 签名后继续执行未声明权限的路由。检查覆盖实际注册路由，白名单是公开接口的明确例外。
- 接口对象权限按已确认的业务关系检查：A 能否访问指定对象须从服务端可信数据判断。对象查询和列表过滤放在 Service 中，必要时由装饰器调用 Service 或由 Service 执行具体归属判断；Resource 不得直接调用 Repository。创建检查目标归属，更新/删除先检查原对象，修改关联时还要检查目标；列表在分页与计数之前过滤。
- 认证得到的用户 ID、角色和状态来自验证后的令牌和可信账号来源；不信任客户端提交的角色、用户 ID 或归属值。不能通过任意字段值碰巧等于用户 ID 推定归属；缺失、重复或不可判断的归属默认拒绝。
- 不允许普通用户通过创建、更新、状态变更等入口修改无权字段（如角色、状态或归属）；分别检查继承字段、显式 `null` 和更改关联的情形。响应不返回密码、密码哈希、密钥或作为普通业务数据的令牌；涉及个人数据或其他敏感字段时按业务规则最小化返回。

### FastAPI 装饰器兼容性

鉴权装饰器需兼容 FastAPI 的参数注入、异步函数和 OpenAPI：使用 `functools.wraps` 保留签名，异步包装器正确 `await`；路由注册装饰器应位于鉴权装饰器外层，确保实际注册的是受保护函数。与项目原有异常处理装饰器共同使用时，认证和授权错误不能被改成 500。针对真实路由验证装饰器顺序、依赖注入、状态码及 OpenAPI，不能以存在装饰器名字代替请求测试。若存在同步接口，需分别正确支持同步和异步。

项目启用 OpenAPI/Swagger 时，声明 Bearer 安全方案并给受保护操作添加相应 `security`，公开登录不要求已有令牌，使文档能够提交认证后的请求。仅 `/openapi.json` 返回 200 不算检查通过；这些声明不能替代实际鉴权。可以用 FastAPI 的认证依赖辅助文档，但受保护接口仍要接入所要求的鉴权装饰器。

## 三、登录和令牌

- 登录入口必须先通过[预检与门禁](preflight-and-gates.md)：无登录或令牌不合格时停止询问，**仅在用户明确同意后**才在原有分层中新增或修订登录。失败统一返回不泄露账号存在性的错误，设置合理的登录失败尝试限制并说明其适用范围，不记录密码、令牌、密钥或其片段。未知历史密码格式不可绕过验证，不擅自重置现有账号；记录兼容或迁移阻碍。脚手架已有 JWT 工具不等于已有登录接口。
- 新密码使用 Argon2id；密码输入、存储和返回遵循安全边界。数据库字段容纳不下哈希时提供必要迁移步骤，按授权范围执行；不能只改临时测试库却交付无法重建的项目。账号准备遵循默认策略中的最小初始化要求，不扩展完整账号管理系统。
- 按 `Authorization: Bearer <token>` 接收 JWT，固定允许的算法并验证签名、过期时间及项目要求的声明。签发、验签和强度检查必须使用同一配置来源；拒绝缺失、默认或弱密钥，配置从受保护环境获取，不写入代码或报告。
- 主体必须映射到唯一、非空的真实账号；令牌验证后按当前可信数据检查账号状态与角色。账号禁用、删除或权限改变的生效方式要与实现和测试一致；无服务端撤销机制时不要声称支持即时注销。
- 未提供或无效令牌返回 401；身份有效但角色不足返回 403。无权对象默认 403，仅当项目明确采用反枚举策略并写进权限说明时才用 404，且状态、业务码、文案必须一致（见第四节）。统一项目的响应格式，不泄露堆栈、密码或令牌。
- 检查认证接入后的异常响应路径：校验错误只返回必要的安全结构，如字段位置、错误类型和固定文案，不回传原始 `input`、请求体或含原始值的异常上下文；日志也不得记录这些内容。错误可能定位到整个 body，其值是嵌套对象或数组，仅按字段名遮盖 `password` 不够。账号认证和恢复秘密的限制见默认策略，内容访问凭据另按明确权限规则处理，不能因管理员身份就直接返回整行数据。
## 四、自助入口、口令与越权响应（强制）

### 1. 自助入口与管理接口二选一，禁止混用

先决定，并写进权限说明；代码与测试必须与该选择一致。

| 方案 | 自助能力 | 资源管理接口 |
| --- | --- | --- |
| A. 提供 `/auth/me`（推荐） | `GET /auth/me` 读本人；`PUT /auth/me` 改本人普通资料；`PUT /auth/me/password` 改密 | `app_user` 等资源的列表/详情/更新/删除/状态**一律要求权限码或管理员**，不再对「本人」放行 |
| B. 不提供 `/auth/me` | 由资源接口承担本人读写 | 资源详情/更新采用「本人 or 权限码」混合判定，必须在权限说明中写明 |

- **禁止既提供 `/auth/me`、又在管理接口里放行「本人」**：两套入口语义重叠，权限判断分叉，测试也说不清预期。
- 自助入口本身只要求已认证，不要求角色/权限码；无任何角色的账号必须可用。
- 列表接口：提供 `/auth/me` 时，资源列表按纯管理权限处理；未提供时默认返回本人，有列表权限码或管理员才返回全部。
- 只读目录（权限点清单、字典、枚举）默认对已登录用户开放读取，写操作才需要管理权限。

### 2. 改密必须是独立接口，资料更新不得校验口令

| 接口 | 请求体 | 校验 |
| --- | --- | --- |
| `PUT /auth/me`（改资料） | 仅普通字段（用户名、邮箱等） | 不校验口令；Schema 中不得出现 `password` / `current_password` |
| `PUT /auth/me/password`（本人改密） | `current_password` + `new_password` | 校验旧口令；缺失/错误 → 400 + `RET.PWDERR`，不写新哈希 |
| `PUT /app-user/{id}/password`（管理员重置，按需提供） | `new_password` | 管理员/专用权限码，记录审计 |

- 禁止把 `password` / `current_password` 放进通用资料 Update Schema：两个动作授权强度不同，混在一起会导致「改个昵称也要密码」或「改密码不校验旧口令」。
- **资源管理接口的 Update Schema 同样不得包含 `password`**（如 `PUT /api/v1/app-user/{id}`）：否则任何被授予 `app_user:update` 的非管理员都能直接重置他人密码，构成账号接管。通用更新带口令字段应返回 422。
- 管理员重置他人密码必须是独立端点（如 `PUT /api/v1/app-user/{id}/password`），挂管理员/专用权限码依赖并记录审计；不得复用通用更新接口。
- 改密成功后旧口令立即失效、新口令可登录；响应不回显任何口令或哈希。
- 管理员重置他人密码不得由普通授权角色复用；重置路径与本人改密路径分开。

### 3. 越权响应：HTTP 状态、业务码、文案三者一致

| 情形 | HTTP | body.code | 文案 |
| --- | --- | --- | --- |
| 未登录 / 令牌无效或过期 | 401 | `RET.SESSIONERR` | 未授权或登录已失效 |
| 已登录但角色/权限不足 | 403 | `RET.ROLEERR` | 无权限执行该操作 |
| 访问他人资源（水平越权） | 403 | `RET.ROLEERR` | 无权访问该资源 |
| 本人改密时旧口令错误 | 400 | `RET.PWDERR` | 原密码错误 |

- 水平越权默认用 **403 + `RET.ROLEERR` + 「无权访问该资源」**；不得返回 404，也不得用「账号不存在」「资源不存在」这类与实际原因不符的文案。
- **密码错误不得复用 `RET.ROLEERR`**：角色/权限错误码只用于授权失败；口令错误用 `RET.PWDERR` 等专用码，避免前端按码分支时误判。
- 只有项目明确采用「反枚举」策略并写进权限说明时，才允许对无权对象返回 404；此时统一用 `RET.URLNOTFOUND` + 「资源不存在」，且不得混用 403 文案。
- 测试必须同时断言 HTTP 状态、`body.code` 与文案，不能只断言状态码。
- 被拒写操作要复查目标记录，确认字段/行数未变化。

### 4. 管理接口必须是声明式权限依赖

- 方案 A 下，资源管理接口（列表/详情/更新/删除/状态）必须在 Resource 上写
  `Depends(require_permission("<资源>:<动作>"))`；**禁止**只写 `require_authenticated`
  再在 Service 里手写权限码判断。
- 权限码判断只允许出现在 `middleware/` 的依赖中，且在启动核对时可枚举；Service 只做数据层与对象层约束
  （唯一性、状态机、归属、字段限制）。方案 B 的「本人放行」属于归属判断，不算第二道权限门。
- 混合写法会让权限判断分叉、启动核对看不出缺口；若确实需要「权限码之外的对象归属」，把它做成
  Service 的数据约束，而不是第二个权限门。

### 5. 列表语义

- 有 `<资源>:list` 权限 → 返回全量（包含本人）；管理员 → 全量。
- 方案 A 下无权限 → 403；方案 B 下无权限 → 仅本人。
- **禁止**「非管理员时排除自己」这类既非本人也非全量的过滤，也禁止返回空列表掩盖权限问题。

### 6. 登录与会话最小声明

- 登录失败统一文案，并对未知账号执行一次 dummy 哈希校验（等时），避免用响应时间枚举账号。
- 失败限流按「账号 + 来源（IP/设备）」计数、阈值可配置；说明进程内计数在多 worker 下独立，
  不能只按用户名计数（否则攻击者可故意失败锁死他人账号）。
- JWT 只放 `sub`（及 `exp`/`iat`）；`roles`/`permissions` 不写入令牌，每次请求按库实时加载，
  避免陈旧授权，也避免让人误以为令牌可携带授权。

### 7. 唯一约束与错误映射

- 用户名、编码等唯一字段冲突必须映射为 409 `ConflictException`（`RET.DATAEXIST`），
  不得抛 500 或把原始 IntegrityError 响应给客户端。
- 更新接口在写入前做冲突检查；并发下捕获 IntegrityError 后同样转 409。

### 8. 交付物（缺一不可）

- `docs/auth-policy.md`：白名单（方法+路径）、权限码映射、角色/对象范围、字段限制、规则来源、受阻范围。
- README / 启动说明同步为「业务接口需要登录」，删除「默认不启用鉴权」等过期描述。
- 初始化脚本实跑一次；权限说明、代码中的 `require_permission` 与测试断言三者必须一致。
