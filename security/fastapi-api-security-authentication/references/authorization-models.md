# 数据权限模型识别与落地

本文件补齐「认证之后」的数据权限：对象归属、租户、组织范围、项目关系、ACL/分享、密级、ABAC、字段级、审批/临时授权、高危操作、职责分离、审计决策、服务账号与场景库。目标是把这些场景从「字段线索」落到**可执行的控制点、统一的拒绝语义和可复跑的验收用例**。

本文件不绑定具体表名或业务产品。表名、字段名只是线索，是否成立要结合注释、外键、Service 查询和需求文字判断；不能因为字段名相似就认定权限模型存在，也不能因为缺少权限说明就放弃识别。

## 一、判定原则

1. **先识别模型，再写代码**。预检脚本把证据汇总在 `authorization_profiles` 与 `scope_fields`；本文件负责把证据翻译成控制点。
2. **主体属性来自服务端**。用户 ID、租户、组织、项目角色、密级、MFA 状态、API Key 范围一律从可信账号/关系表加载，不接受请求体、URL 参数或客户端 JWT 自报值。
3. **拒绝优先**。显式拒绝 > 强制义务（MFA/审批/密级）> 允许规则 > 默认模式（默认拒绝）。
4. **统一响应语义**。未登录 401；身份有效但动作不允许 403；无权对象按项目约定 403 或反枚举 404，同一项目内必须一致；需要 MFA/审批时返回 403 或明确的待办语义，不得静默放行。
5. **列表先过滤再分页计数**。任何数据范围都必须在 `count` 与 `offset/limit` 之前进入 `WHERE`，不能先查全量再在 Python 里截断。
6. **服务端字段不可由客户端赋值**。归属、租户、组织、项目、角色、状态、密级、审批结果、API Key 摘要等字段不得出现在 Create/Update 的可写字段中；显式 `null` 同样要拦截。
7. **写操作先判原对象**。更新/删除/状态变更必须先按服务端读取的原对象做权限判断，再判断目标关联；不能只看请求里的新归属。
8. **被拒绝的写操作要查库确认无副作用**。

## 二、识别信号

运行预检脚本后读取 `authorization_profiles`（每项包含 `id`、`confidence`、`evidence`、`required_controls`、`acceptance_cases`）和 `scope_fields`（按表列出 ownership/tenant/org/project/role_status 字段）。常见信号：

| 模型 id | 表/字段线索 |
| --- | --- |
| `object_ownership` | `owner`、`owner_*_id`、`created_by`、`creator*`、`author_id`、`uploader*` |
| `tenant_isolation` | `tenant_id`、`tenant_code`、`tenant` 表 |
| `org_scope` | `org_unit_id`、`org_id`、`department_id`、`parent_org_unit_id`、`org_member`、`member_role` |
| `project_rebac` | `project`、`project_member`、`project_id`、`parent_project_id`、`member_role` |
| `acl_grant` | `resource_grant`、`*_grant`、`grantee_user_id`、`can_view`、`can_edit`、`can_reshare` |
| `share_lifecycle` | `resource_share`、`share_token`、`max_access_count`、`allow_download`、`allow_reshare` |
| `classification` | `classification_level`、`classification*`、`security_level`、`requires_approval`、`requires_mfa` |
| `abac_policy` | `abac_policy`、`condition_json`、`effect`、`priority`、`missing_attribute_behavior` |
| `field_level` | `field_policy`、`field_code`、`access_mode`、`mask_pattern` |
| `approval_temp_grant` | `access_request`、`approval_task`、`applicant_user_id`、`step_no`、`resource_grant.valid_to` |
| `high_risk_break_glass` | `high_risk_operation`、`break_glass_request`、`user_mfa`、`mfa_verified` |

| `audit_decision` | `audit_event`、`authorization_decision`、`is_auditor`、`deny_reason` |
| `service_account` | `service_account`、`api_key`、`key_hash`、`scopes`、`delegation` |

| `behavior_config` | `platform_config`、`config_key`、`value_type` |

## 三、通用执行模型

每次受保护请求按五元组判定：`主体(subject) × 资源(resource) × 动作(action) × 上下文(context) × 决策(decision)`。

| 检查点 | 实现位置 | 要求 |
| --- | --- | --- |
| 主体 | `middleware/` 认证依赖 + Service 加载关系 | 只信任服务端；每次请求按当前库状态加载角色、租户、组织、MFA 等 |
| 资源 | Service | 先按主键取原对象；不存在与无权按约定语义处理，不能泄露存在性 |
| 动作 | Resource 声明式依赖 + Service 数据约束 | 权限码/角色门在 `middleware/`；归属/范围/状态机在 Service |
| 上下文 | 服务端采集 | IP、时间、设备、MFA 状态不能由请求体自报 |
| 决策 | 统一入口 | 返回 allow / deny / need_mfa / need_approval，并记录命中规则与拒绝原因 |

推荐在 Service 内集中一个 `_authorize(action, obj, principal)`，各入口只调用它，避免同一资源不同入口各写一套判断。

## 四、逐模型规格

### 1. 对象归属与水平越权（`object_ownership`）

**必做控制**

- 创建：服务端写入归属字段，忽略或拒绝客户端提交的归属值。
- 详情/更新/删除/状态：按服务端原对象归属判断；普通用户只能操作本人，管理员按规则放行。
- 列表：在分页与计数前按归属过滤。
- Update 可写字段排除归属、状态、角色等无权字段。
- 被拒绝的写操作查库确认未变化。

**响应语义**：默认 403 + 「无权访问该资源」；项目明确反枚举时统一 404 + 「资源不存在」。

**验收用例**：本人读 200；他人读/改/删被拒且数据不变；列表只含本人；创建提交他人归属不生效；更新篡改归属/状态不生效；管理员可管理全部。

**反模式**：客户端传什么 owner 就存什么；列表先查全量再过滤；只在详情拦截、更新/删除直通。

### 2. 多租户隔离（`tenant_isolation`）

**必做控制**

- 所有查询强制带 `tenant_id`，值来自已认证主体。
- 请求参数中的租户标识不得覆盖身份租户；冲突时拒绝并记录安全事件。
- 跨租户读/改/删统一按约定返回 403 或 404。
- 租户禁用/归档后，该租户普通成员被拒；平台管理员按明确规则处理。
- 租户管理员只能管理本租户。
- 列表计数按租户过滤。

**验收用例**：同租户 200；跨租户读/改/删被拒且数据不变；篡改 `tenant_id` 无效；租户禁用后 401/403；跨租户管理被拒；列表总数只统计本租户。

**反模式**：只过滤列表不过滤详情；从请求体取 `tenant_id`；用资源 ID 是否存在判断权限。

### 3. 组织/部门数据范围（`org_scope`）

**必做控制**

- 从服务端组织树计算可见组织集合：本人组织 + 下级组织；经理按规则扩展。
- `org_member` 等附加关系校验 `valid_from` / `valid_to` / `status`，到期或移除立即失效。
- 外部合作组织（如 `org_type=5`）与内部组织互相隔离。
- 请求中的组织标识只能作为筛选提示，不能扩大范围。
- 列表在计数前按组织范围过滤。

**验收用例**：本人数据；经理本部门及下级；经理跨部门被拒；外部/内部互访被拒；组织调整后按新范围；参数篡改无效；临时成员到期/移除后被拒。

**反模式**：只判断 `org_id` 相等、不递归下级；信任请求里的组织 ID；不校验成员有效期。

### 4. 项目成员与关系权限（`project_rebac`）

**必做控制**

- 项目成员关系是唯一关系来源；按 `member_role` 执行动作矩阵（Owner/Admin/Editor/Viewer）。
- 非成员按约定 404/403；成员被移除或 `status=0` 后下一次请求立即失效。
- Viewer 只读；Editor 可编辑不可删除/授权；Owner/Admin 可管理。
- 嵌套项目：父项目成员默认继承子项目查看能力，编辑/删除/授权仍需子项目成员资格；检测循环并返回 409。
- `project_id` / `member_role` 不能由客户端篡改。

**验收用例**：成员查看 200；非成员被拒；Viewer 编辑被拒；Editor 删除被拒；Owner 管理成功；移除成员后被拒；归档后新增/编辑被拒；嵌套继承与循环检测。

### 5. ACL、授权与分享生命周期（`acl_grant` / `share_lifecycle`）

**必做控制**

- 资源所有者可授权/撤销；管理员按规则管理全部。
- 被授权用户按 `can_view` / `can_edit` 执行动作；`valid_to` 过期、`status` 撤销/过期立即失效。
- `can_reshare=0` 的受托人不能再次分享。
- 分享校验：令牌摘要、密码哈希、有效期、最大访问次数、`allow_download`、`allow_reshare`。
- 资源状态机：冻结只读、归档不能新分享、删除后普通入口按约定不存在。
- 授权/撤销/分享访问写审计。

**验收用例**：直接授权可读；撤销/过期后被拒；错误密码/次数用尽被拒；禁止下载被拒；冻结后编辑被拒；归档后新分享被拒；删除后访问不存在；禁止转分享被拒。

**反模式**：只校验令牌存在、不校验状态和次数；把分享密码明文存储；冻结/归档只在前端限制。

### 6. 资源密级（`classification`）

**必做控制**

- 资源必须绑定密级；密级规则决定查看、下载、分享的前置条件。
- 机密需已通过审批；绝密还需 MFA；绝密默认禁止下载/分享。
- 密级是强制限制，**管理员不能自动绕过**。
- 密级变更后下一次请求按新规则判定。
- 用户安全等级只作为策略输入，不自动等同资源密级。

**验收用例**：公开/内部可读；机密无审批被拒、有审批通过；绝密无 MFA 被拒；绝密下载/分享被拒；管理员访问绝密同样受限；密级变更即时生效。

### 7. ABAC 属性策略（`abac_policy`）

**必做控制**

- 统一策略引擎输入主体、资源、动作、上下文属性。
- 条件支持 AND/OR/NOT；**显式拒绝优先于任何允许**，不能被管理员或所有权覆盖。
- 多规则按 `priority` 排序；同优先级冲突时拒绝优先。
- 属性缺失按策略声明的 `missing_attribute_behavior`；无策略时按配置默认（默认拒绝）。
- 环境属性（IP、时间、设备、MFA）服务端采集。
- 策略修改前保存版本快照；恢复旧版本要审计。
- 每次决策记录命中策略、结果、拒绝原因（区分「无允许规则」与「显式拒绝」）。

**验收用例**：同部门允许；跨部门拒绝；显式拒绝压过允许；属性缺失按默认；优先级生效；未 MFA 被拒；客户端伪造属性被忽略；版本快照与恢复。

### 8. 字段级权限、脱敏与导出（`field_level`）

**必做控制**

- 字段策略按角色/字段/访问模式（可见、只读、脱敏、隐藏）配置；无匹配时按默认。
- 列表、详情、导出共用同一投影函数；隐藏字段不返回，脱敏字段返回掩码。
- 只读字段不可写；隐藏字段提交应拒绝或剔除。
- 导出权限独立于查看权限，导出内容同样过滤。
- 审计记录敏感字段访问，但不返回原始值。

**验收用例**：普通用户详情隐藏/脱敏正确；列表同样过滤；无导出权限被拒；经理导出按策略；只读字段修改被拒；隐藏字段提交不生效；策略变更即时生效。

### 9. 权限申请、审批与临时授权（`approval_temp_grant`）

**必做控制**

- 申请包含资源、动作、原因、期望有效期；生成审批任务。
- 申请人不能审批自己的申请；无审批资格返回 403。
- 单人/双人审批；双人必须是两个不同审批人。
- 审批通过生成有 `valid_to` 的临时授权；到期/撤销立即失效。
- 执行前重新校验申请人当前权限；权限已撤销则不得执行。
- 同一申请的操作只能执行一次，重复执行 409。
- 审批记录不可被普通管理员修改/删除。

**验收用例**：提交 201；自审批 403；单人/双人流程；到期/撤销后被拒；执行前复核；重复执行 409。

### 10. 高危操作、MFA 与 Break-glass（`high_risk_break_glass`）

**必做控制**

- 高危操作在审批通过前不得执行；执行前必须完成 Step-up MFA，否则 403。
- 双人审批需两个不同审批人；发起人不能自批。
- 执行前复核发起人权限与账号状态。
- 同一操作只能执行一次，重复 409。
- Break-glass 必须填写原因、范围、有效期；到期/撤销立即失效；结束后进入事后审查。
- 所有高危与紧急访问完整审计，不可删除。

### 11. 职责分离与权限撤销（`sod`）

**必做控制**

- 互斥角色不能同时授予；`enforcement=禁止分配` 返回 409，`仅告警` 允许但写冲突记录。
- 角色撤销/禁用后，通过该角色获得的能力下一次请求立即失效。
- 权限每次请求实时加载，不长期缓存；客户端提交角色参数无效。
- 冲突记录包含用户、规则、发现时间、处理状态、处理人。

### 12. 审计与授权决策（`audit_decision`）

**必做控制**

- 每次访问决策写 `authorization_decision`：用户、资源、动作、结果、原因、命中规则。
- 登录、登出、权限变更、资源访问、拒绝访问写 `audit_event`。
- 拒绝原因区分「无允许规则」与「显式拒绝」。
- 审计/决策只追加，不提供普通更新/删除；只有审计员或管理员可查。
- 日志不含密码、哈希、完整令牌、密钥。

### 13. 服务账号、API Key 与委托（`service_account`）

**必做控制**

- 服务账号不继承用户/管理员权限；必须设置责任人与明确范围。
- API Key 只存摘要，创建时一次性返回明文；过期、撤销、账号禁用后 401。
- `scopes` 限制动作；超范围 403。
- 委托只能转授委托人自身拥有的权限，必须有有效期；到期/撤销立即失效；未经允许不得再委托。

### 14. 场景库（`scenario_library`）

**必做控制**

- 场景包含主体、资源、动作、上下文、期望决策；分类覆盖跨组织、横向、纵向、边界、时序、异常输入。
- 执行场景调用统一鉴权入口，实际决策与期望比对；不一致标记失败并记录差异。
- 停用场景不参与执行；场景库不预置漏洞、不生成攻击脚本、不修改业务数据。

### 15. 鉴权行为配置（`behavior_config`）

**必做控制**

- 配置键至少覆盖：默认拒绝/允许、跨组织返回 403/404、权限变更会话失效策略、属性缺失默认、无字段权限 omit/mask、审批超时。
- 仅管理员可改；按 `value_type` 校验；非法值 400/422 且配置不变。
- 修改后对后续请求生效；客户端参数不能覆盖服务端配置；变更审计含前后值。
- 配置缺失时使用安全默认值（默认拒绝）。

## 五、组合与优先级

同一资源命中多个模型时，按以下顺序求值，任一拒绝即拒绝：

```text
认证 → 租户 → 组织/项目范围 → 对象归属 → ACL/分享 → 密级 → ABAC 显式拒绝 → ABAC 允许 → 审批/临时授权 → 高危 MFA → SoD → 字段投影 → 默认模式
```

- 显式拒绝和强制义务不能被管理员、所有权或 ACL 覆盖。
- 字段投影最后执行，只影响返回内容，不改变是否允许访问。
- 决策记录必须包含命中的模型与规则，便于追溯。

## 六、交付与测试

每个检测到的模型至少交付：

1. 权限说明中的一行：模型、触发证据、主体来源、数据范围、动作矩阵、响应语义。
2. 代码控制点：认证依赖、Service 范围过滤/归属判断、字段保护、审计写入。
3. 至少一组正向 + 拒绝用例，断言 HTTP 状态、`body.code`、文案与数据库前后状态。
4. 列表用例单独断言总数与分页，不能只断言返回 200。
5. 写明未覆盖或证据不足的模型，不得用「已加管理员门」代替。

## 七、与门禁的衔接

- 门禁 1–5 通过后，执行**门禁 6**读取 `authorization_profiles`，逐项确认或标记「证据不足/不适用」。
- 门禁 6 未完成，不进入数据权限实现；实现后按[测试与验收](testing-and-acceptance.md)第六节复跑。
- 任何模型的控制点缺失，都必须在 `docs/auth-policy.md` 与报告中列为缺口，不能宣称已覆盖。
