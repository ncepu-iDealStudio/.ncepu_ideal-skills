# 五段认知逻辑与写作技巧

每个知识点的讲义正文，都按下面五段顺序展开。这五段对应学生"从零到会用"的认知过程，顺序不可颠倒。每段的篇幅不必均等——重点段落多写，次要段落精简，但五段都要有内容。

> **重要**：五段是**内在的叙事顺序**，不是要贴五个标题。好的讲义不顶着"一、是什么 / 二、为什么会出现"这样的标题，而是用**认知钩子**分节（如「一个代词引出的难题」→「在 X 之前：逐个处理的老办法」→「关键转折：让每个词直接看整句」→「动手一：用最小代码看清一件事」）。生成器要**把五段内化成叙事**，按具体内容拟定有信息量的小节标题；只有在知识点简单、确实需要显式骨架时才直接用五段名做标题。

## 写之前的四条基调

这四条贯穿全文，比任何单段技巧都重要，是教材可读性的主要来源：

1. **用学生亲身经历的问题开场，不用定义开场，也不用行业场景开场。** 一段的第一句最好是一个学生自己也经历过、会好奇的问题或现象，然后再引出概念。场景够不够贴近，按下面「场景选择」一节判断。
2. **全程第二人称。** 写"你会看到""你可以把它想象成""你敲下回车"，不写"读者将会看到"。教材是和老师面对面讲，不是写文档。
3. **术语第一次出现就解释。** 括号里给全称 + 中文 + 一句大白话类比，如"HTTP（HyperText Transfer Protocol，超文本传输协议，是客户端和服务器之间最常用的『送信规矩』）"。后续再用就不重复解释。
4. **诚实标注来源与验证状态。** 引用外部资料、图、代码或数值时，写明出处；自己没跑过的示例写清"未独立复跑"；示意图数值与代码实际输出不一致时明确说明。不知道精确年份就用"约""21 世纪初"，宁可模糊也不要编造。

## 场景选择：所有例子都从学生生活里来

**这是全技能优先级最高的内容规则，先于任何写作技巧。** 讲义里出现的**每一个**场景——开篇钩子、生活类比、示例代码的输入数据、练习的业务背景、配图里的示意——都必须来自学生已有的生活经验，或来自本课程前面已经学过的内容。学生不需要任何额外背景就能直接进入。

**判断标准只有一句：学生亲眼见过、亲手做过吗？**

- 能，且不用再解释背景 → 用。
- 需要先花一段解释"这是啥、为什么会这样" → 换掉。

**优先使用的场景库**：注册账号时填邮箱和手机号、登录验证、搜索、聊天消息、朋友圈、网购与快递单号、游戏数值与排行榜、成绩单与课程表、手机相册、之前学过的变量/列表/函数。

**禁止使用的场景库**：工单系统、日志分析、订单流水、ERP、运维告警、供应链、金融风控、物联网遥测——除非教学对象本来就在该行业工作，且提纲里已确认。这些场景对写教案的人很自然，对学生很陌生；越"专业"的例子反而越难懂。

**同一知识点，两种开场对比**（以正则表达式为例）：

反面——学生还没学正则，先要搞懂"工单"是什么、谁会写这种备注：

> 假设你收到一条工单备注：`Assigned TK-1024; closed TK-2048.`。你想把两个工单编号都取出来……

正面——学生自己干过这件事，问题一抛出来就想追着看：

> 你注册一个网站，邮箱栏随手填了 `abc`，系统立刻提示"请输入正确的邮箱"。你又填 `abc@`，还是不对。它凭什么知道你在瞎填？这套判断规则，就是正则表达式。

**代码和练习同样受此约束**：示例里的字符串用 `user@example.com`、`13800138000`、一段聊天消息这类学生见过的东西，不要用 `TK-1024`、`ORDER-2024-001` 这类凭空设定的业务编号。练习的业务背景同理。

**注意**：贴近生活不等于牺牲准确性。如果生活场景的真实规则很复杂（例如完整邮箱规则远不止"有个 @")，要在代码前声明简化边界——"我们先看一个够用的简化版，它挡得住随手乱填，但挡不住格式正确却不存在的邮箱"——而不是选一个晦涩场景来回避这件事。

## 第一段：是什么（建立第一印象）

**目的**：让学生用 30 秒建立直觉，知道"这东西大概是个啥"。

**写法**：
- 先抛一个具体问题或现象（"先把这句英文翻译一下……`it` 指谁？"），再给直觉定义（用生活类比），最后给规范定义。
- 用一个具体例子把它具象化："比如你访问一个网页时……"
- 点明它处在什么位置、和谁打交道（上下游关系）。
- 术语首次出现按上面的第 3 条即时解释。

**示例骨架**：

> 先看一个场景：______。你会发现 ______。
> 你可以把它想象成 ______。正式地说，X 是 ______（英文全称与中文解释）。它位于 ______ 和 ______ 之间，负责 ______。

**避免**：开头就甩形式化定义或官方术语堆砌；标题叫"是什么"却没有一个具体场景。

## 第二段：为什么会出现（交代问题背景）

**目的**：让学生明白"没有它之前有什么痛点"，从而理解它存在的价值。

**写法**：
- 描述当时的具体困境：在没有 X 的年代，人们遇到什么问题？
- 给出量化的或具象的痛点（慢、贵、易错、难维护、规模上不去），"具象数字"优于"很慢很快"。
- 过渡："为了解决这个问题，人们尝试了……，直到 X 出现。"

**示例骨架**：

> 在 X 出现之前，大家这样做：______。但这带来几个麻烦：一是 ______，二是 ______。
> 随着 ______ 的发展，这些问题越来越突出。X 就是为了应对这个局面被提出来的。

**避免**：直接跳到"X 有很多优点"——没讲清痛点，优点就没有说服力。

## 第三段：发展历程（建立时间线）

**目的**：让学生看到技术演进的脉络，理解"为什么长成现在这样"。

**写法**：
- 按时间列出 3～5 个关键节点：起源 → 关键改进 → 成熟/普及 → 近期演进。
- 每个节点说清"谁、大约什么时候、解决了什么、留下了什么问题"。
- 配一条时间线 Mermaid 图（`timeline` 或流程图）；按 `assets-guide.md` 的约定，同时导出 PNG 并保留 `.mmd` 源码。

**示例骨架**：

> - **起源（约 19xx）**：______，解决了 ______，但 ______。
> - **关键改进（约 19xx）**：______ 提出 ______，突破了 ______。
> - **成熟普及**：______ 成为事实标准，因为 ______。
> - **近期**：______ 方向上仍在演进，如 ______。

**避免**：编造具体人名年份。不确定的年份用"约""21 世纪初"这类模糊表述，或只讲阶段不讲精确时间。

## 第四段：应用现状（连接真实世界）

**目的**：让学生知道"这东西现在用在哪、值不值得学"。

**写法**：
- 列 3～5 个真实应用场景，每个说清"在这里它承担什么角色"，不要只列名字。
- 提到主流工具/产品/框架中的落地（可写具体名字）。
- 客观说明局限：什么场景下不适合用、有什么替代方案。
- 可直接点明"这对写代码意味着什么"，把知识和学生要做的事挂钩。

**示例骨架**：

> X 现在广泛应用于：______（用于 ______）、______（用于 ______）。
> 在主流工具如 ______ 中，X 是核心机制之一。
> 不过 X 并不万能：在 ______ 场景下，人们更常用 ______，因为 ______。

**避免**：只讲好的不讲局限；列举没有具体角色的"应用场景清单"。

## 第五段：如何开始使用（落到实操）

**目的**：让学生"读完就能动手"，这是自学材料的收尾落点，篇幅也最足。

**写法**：
- **前置准备**：需要什么环境/依赖，一句话说清；可选依赖写明"装不上就跳过，不影响后续"。
- **最小可运行示例**：给一段最短代码或最少步骤，配"预期你会看到 ______"。
- **讲解与代码的关系**：代码是论证链的一环，不是附件。代码前声明简化边界（"它比真实模型简陋得多，但足以让你亲眼看到……"），代码后用真实输出做解读，并把结论接回前面的原理。详见 `assets-guide.md`。
- **逐步深入**：给 2～3 个递进的小任务，每个比上一个多一点变化；任务绑定具体示例文件并给验收条件。
- **链接配套示例**：指向 `examples/` 中的完整示例目录。
- **常见坑**：列 2～3 个新手最容易踩的坑及解法。
- **小结 + 思考题**：一段话收束全文，留 2～3 道思考题（答案可不给，供自测）。

**示例骨架**：

> ### 环境准备
> 需要 ______，安装：`______`。可选依赖 `xxx` 装不上就跳过，不影响后面。
>
> ### 动手一：用最小代码看清一件事
> 下面这段只做 ______（简化边界：它不做 ______，但足以说明 ______）。
>
> ```python
> # 最短可运行示例
> ```
>
> ```bash
> python examples/01-xxx/main.py
> ```
>
> 运行后你会看到 ______。原因很直白：______。这也解释了前面讲的 ______。
>
> ### 再进一步
> 把 `examples/01-xxx/main.py` 里的 ______ 改成 ______，观察 ______。验收条件：能说明 ______。
> 完整示例见 [`examples/01-xxx/`](../examples/01-xxx/)。
>
> ### 常见坑
> | 现象 | 原因 | 解决 |
> | --- | --- | --- |
>
> ### 小结
> 这一篇我们讲了 ______。一句话带走：______。下一节 ______。
>
> ### 思考题
> 1. ______？
> 2. ______？

**避免**：只给代码不给预期输出；示例太长吓退新手；代码与讲解各说各的；没有收尾小结。

## 生动通俗的通用技巧

| 技巧 | 怎么用 | 例子 |
| --- | --- | --- |
| 问题式开篇 | 用学生自己也好奇的问题或反常识现象起头 | "同一个 `it`，一句指动物、一句指街道，机器怎么分？" |
| 生活类比 | 把抽象机制映射到日常经验 | "三次握手就像两个人隔着嘈杂的房间确认彼此能听见" |
| 第二人称 | 全文用"你"，像面对面讲 | "你在网页聊天框里敲下……，0.8 秒后答案出现了" |
| 术语即释 | 第一次出现的术语在括号里给全称+中文+大白话 | "API（Application Programming Interface，程序之间约定好的『点菜方式』）" |
| 先问后答 | 每段开头先抛一个问题再解答 | "为什么不能只握两次手？" |
| 具象数字 | 用具体数量级代替"很慢/很快" | "1 毫秒 vs 100 毫秒，用户能明显感到卡顿" |
| 视觉化 | 关键流程配图（Mermaid 导出 PNG + 保留 `.mmd`） | 时序图、流程图、架构图 |
| 递进重复 | 同一概念先用大白话讲一遍，再用术语精确化 | 先"像快递中转站"，再"代理节点的职责是……" |
| 一句话提炼 | 复杂规则讲完，用一句加粗的话收口 | "**一句话**：订阅买的是用网页的权利，API 买的是程序调用权" |
| 过渡句 | 段与段之间加一句承上启下 | "明白了它是什么，接下来看它为什么会出现。" |
| 加粗锚点 | 每节加粗 1～2 个关键词，方便略读回看 | **可靠传输**、**拥塞控制** |
| 诚实标注 | 外部资料写图源/出处；未复跑的示例写明；示意数值与实际输出不符要说明 | "这段输出引自 XX，本环境未独立复跑" |

## 分层阅读路径

一套教材要照顾不同时间预算的学生。在每个章 README 与关键讲义里，给出一条**快速路径**：

- "如果你只有二十分钟：读 X 的第 1、5 节，再跳到 Y 的动手部分，最后跑一遍 Z。"
- 明确哪些段落可跳过、跳过后补回来会更有感觉，不要让学生自己猜。

## 篇幅建议

- 单个知识点全文：2000～3500 字为宜
- 五段参考配比：是什么 15% / 为什么 15% / 发展历程 15% / 应用现状 20% / 如何开始使用 35%
- 「如何开始使用」是自学落地的关键段，篇幅应最足

## 认知顺序自检

生成后逐条对照：

- [ ] 第一段用学生亲身经历的问题或场景开场，给了直觉定义，不是一上来就甩公式
- [ ] 全篇每一个场景（开篇、类比、示例输入、练习、配图）都是学生经历过的？有没有需要先解释背景的行业场景？
- [ ] 第二段讲清了"没有它会怎样"的痛点，用了具象数字
- [ ] 第三段有时间脉络，且没有编造精确年份
- [ ] 第四段的应用场景都说明了"承担什么角色"，并讲了局限
- [ ] 第五段有环境准备、简化边界声明、最小示例、真实输出解读、验收条件、思考题
- [ ] 五段顺序正确，但小节标题是拟定的信息型标题，不是生硬的"是什么/为什么"
- [ ] 全文用第二人称，术语首次出现有解释
- [ ] 外部资料、图、未复跑的示例都有来源与验证状态标注
