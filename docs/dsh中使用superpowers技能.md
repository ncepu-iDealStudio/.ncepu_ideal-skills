# 在 DSH 中使用 superpowers 技能

> 面向第一次在 DSH（DeepSeek Harness）里使用技能的同学。照着本文走完，你能从"一句模糊的想法"开始，用 superpowers 技能链完成需求分析、方案设计、实现计划，直到可运行的代码。
>
> 全文以一个具体教学范例贯穿：**校园技能互换社交 App**。

---

## 1. 先搞清楚：DSH 怎么找到技能

DSH 启动时会扫描若干目录，把发现到的技能以「名称 + 描述摘要」的形式放进会话的技能目录（catalog）。你不需要手动 import 任何东西。

### 1.1 技能搜索路径

项目级（优先级高，随仓库走）：

```text
<项目根>/.dsh/skills/<技能名>/SKILL.md      # DSH 原生目录
<项目根>/.agents/skills/<技能名>/SKILL.md   # 通用 Agent Skills 目录，DSH 同样扫描
```

用户级（对所有项目生效）：

```text
~/.dsh/skills/<技能名>/SKILL.md
~/.agents/skills/<技能名>/SKILL.md
```

也支持**扁平 Markdown 技能**：直接把一个 `.md` 文件放在 `skills/` 下，文件本身即技能。

### 1.2 SKILL.md 的必备结构

每个技能是一个目录，核心是 `SKILL.md`，开头必须有 YAML frontmatter：

```markdown
---
name: brainstorming
description: "在任何创造性工作之前必须使用此技能——创建功能、构建组件……"
---

# 技能正文
...
```

- `name`：技能标识，**同一目录下必须唯一**
- `description`：决定"什么时候该触发"，写得好坏直接决定技能会不会被用起来
- 正文：具体流程、检查清单、反模式。技能是给模型读的作业指导书，不是给人读的营销材料

### 1.3 怎么触发一个技能

三种方式，效果等价：

| 方式 | 做法 | 适用 |
| --- | --- | --- |
| 点名 | 直接说"用 brainstorming 技能" | 你明确知道要用哪个 |
| 描述匹配 | 说出与 `description` 吻合的任务，如"我们要开发一个新系统" | 日常最常用 |
| 由其他技能转交 | 如 brainstorming 结束时自动转给 writing-plans | 链路式工作流 |

> **重要**：技能的价值不在"知道有它"，而在"按它的流程真的走一遍"。superpowers 的每个技能都带检查清单和反模式，跳步是它最想拦住的事。

## 2. 本仓库里有哪些 superpowers 技能

仓库同时装了两套来源：

- **`.agents/skills/` 与 `.codebuddy/skills/`**：superpowers-zh 中文本地化版，20 个技能
- **`.dsh/skills/`**：面向 DSH 的原生目录，装 `common-website-design`、`it-requirement-analysis`、`prd-html`、`diagnosing-superpowers`

### 2.1 常用技能速查

| 阶段 | 技能名 | 什么时候用 |
| --- | --- | --- |
| 入口 | `using-superpowers` | 对话开始，确立"先找技能再动手"的习惯 |
| 需求 | `requirement-analysis` | 业务诉求 → PRD、用户故事、验收标准 |
| 设计 | `brainstorming` | 任何创造性工作之前：探索意图、比选方案、出设计 |
| 规划 | `writing-plans` | 有了规格，写多步骤实现计划 |
| 执行 | `executing-plans` / `subagent-driven-development` | 按计划分任务推进，带审查检查点 |
| 编码 | `test-driven-development` | 写实现之前先写测试 |
| 排错 | `systematic-debugging` | 遇到 bug、测试失败，先定位再修 |
| 审查 | `requesting-code-review` / `receiving-code-review` | 完成任务后验证，以及接收反馈 |
| 收尾 | `verification-before-completion` | 宣称"完成"之前，必须跑验证命令 |
| 复盘 | `diagnosing-superpowers` | 会话跑歪了，回溯原因、生成排障报告 |
| 原型 | `prd-html` | PRD → 可点的 HTML 交互原型 |
| 网站设计 | `common-website-design` | 自然语言 → 框架无关的静态网站设计原型 |

### 2.2 目录名 ≠ 技能名（容易踩的坑）

技能在目录里叫什么，和它 frontmatter 里的 `name` **未必一致**。DSH 认的是 `name`：

| 目录名 | frontmatter `name` |
| --- | --- |
| `it-requirement-analysis` | `requirement-analysis` |
| `prd-html-skill` | `prd-html` |
| `common-website-design` | `common-website-design` ✓ 一致 |
| `diagnosing-superpowers` | `diagnosing-superpowers` ✓ 一致 |

所以本文用 `name` 指代技能（如 `requirement-analysis`），而在讲文件路径时用目录名。

### 2.3 技能之间的关系

superpowers 不是一堆并列工具，而是一条**带关卡的主线**：

```text
using-superpowers（习惯）
        │
        ▼
requirement-analysis（需求）──► prd-html（可选：原型）
        │
        ▼
brainstorming（设计 + 规格文档）
        │
        ▼
writing-plans（实现计划）
        │
        ▼
executing-plans / subagent-driven-development（执行）
        │
        ├──► test-driven-development（写码）
        └──► systematic-debugging（错了）
        │
        ▼
requesting-code-review ──► verification-before-completion（完成）
```

## 3. 教学范例：校园技能互换社交 App

### 3.0 场景设定

**背景**：某大学（下文以"华电"代称）有 2 万余名在校生。学生之间普遍存在"我会的东西正好是你要学的、你想学的正好是别人会的"现象，目前靠微信群、贴吧零散撮合，存在三个痛点：

1. **撮合效率低**：发帖没人看，需求沉底
2. **信任成本高**：不知道对方水平和靠谱程度
3. **约不上**：谈好了时间地点，一方爽约也没有约束

**想法（初始诉求）**：

> "我想做一个校园内的技能互换社交 App，比如我会摄影、想学吉他，就在平台上找到一个会吉他、想学摄影的人，我们互相教对方。"

这个诉求**信息量很低**：没说用户规模、没说什么叫"换成功"、没说要不要校内实名、没说预算和工期。这正是技能链要解决的问题——**把一句话变成可开发的东西**。

---

### 3.1 第一步：用 `requirement-analysis` 做需求分析

**触发方式**：说出任务即可，例如

```text
我们学校想做一个校园技能互换社交 App，帮同学互相教技能。
请用需求分析的方法，帮我把这个想法梳理成可落地的需求。
```

技能会按 **6 步法**推进：需求采集 → 需求澄清 → AI 应用评估 → 需求分析 → 输出呈现 → 总结行动建议。

#### 关键环节一：澄清（选择题式追问）

技能的原则是「不清楚就问，尽量用选择题」。它会一次性问你几个只有你能回答的问题：

```text
📋 需求澄清

1. 使用对象
   [A] 全校学生（需实名/学号认证）
   [B] 仅本学院试点
   [C] 校内外都可参与

2. 交换形态
   [A] 一对一互教（A 教 B 摄影，B 教 A 吉他）
   [B] 技能市集（发需求/发供给，自由撮合）
   [C] 两种都要

3. 撮合方式
   [A] 人工审核后匹配
   [B] 系统按标签/兴趣推荐
   [C] AI 语义匹配（描述"我会的/我想学的"自动配对）

4. 首期目标
   [A] 验证需求，3 个月内跑通 100 对
   [B] 覆盖全校，正式运营

请选择（可多选，也可补充"其他"）
```

假设你回答：**A 全校实名 / C 两种都要 / C 要 AI 匹配 / A 先验证**。

#### 关键环节二：AI 应用评估

技能会主动评估"这件事哪里该用 AI"，而不是默认传统方案。对本项目的结论大致是：

| 环节 | AI 适用性 | 推荐能力 |
| --- | --- | --- |
| 技能匹配 | ⭐⭐⭐⭐⭐ | 用自然语言描述"我会的/我想学的"，语义向量召回 + 重排 |
| 技能描述结构化 | ⭐⭐⭐⭐ | 用户只写一句"会修电脑"，LLM 补全为结构化标签 |
| 内容安全 | ⭐⭐⭐⭐ | 违规文本/图片识别 |
| 互评总结 | ⭐⭐ | 可选，收益低 |

这一步很关键：**它把"要写一个推荐算法"这种模糊说法，落成了"用 embed + 向量库召回 + 规则重排"这种可估工的东西**。

#### 关键环节三：结构化输出

技能不会一次性倒给你 30 页 PRD，而是**先给摘要**，让你选深入哪一块：

```text
📋 需求摘要

【需求名称】校园技能互换社交 App
【核心功能】技能名片 · 双向撮合 · 预约履约 · 互评信用
【AI 方案】⭐ 推荐 —— 语义匹配 + 描述结构化 + 内容风控
【用户】全校实名学生
【首期目标】3 个月跑通 100 对有效互换
【核心风险】冷启动供给不足、爽约率、隐私边界

请选择要深入的部分：
[A] 完整 PRD   [B] 用户故事+验收标准   [C] AI 方案详情
[D] 功能清单+优先级矩阵   [E] 实施计划   [F] 全部展开
```

选定后，技能会加载对应模板（`references/prd-template.md`、`references/user-stories.md`、`references/process-analysis.md`）产出正文。

#### 这一步的产出物

- **PRD**：背景、角色、核心流程、功能清单（F01…）、非功能需求
- **用户故事 + 验收标准**：如「作为想学吉他的学生，我能看到 3 个匹配候选及其信用分，以便决定联系谁」+ Given/When/Then 验收条件
- **功能优先级矩阵**：P0/P1/P2 与 MVP 边界
- **需求评分卡**：业务价值/用户清晰度/技术可行性/落地性，一眼看出需求质量

> **这一步刻意不写代码、不选技术栈**。需求阶段混入技术决策，后面就没有回头路。

---

### 3.2 第二步：用 `brainstorming` 做设计

拿到 PRD 后进入设计。先判断路径——这是 superpowers 很重要的一条纪律。

#### 路径判定

`brainstorming` 把任务分成三类，**拿不准时选更重的那条**：

| 路径 | 判定标准 | 产出 |
| --- | --- | --- |
| 探路 Spike | 可行性问题（"AI 匹配到底准不准？"） | 一个答案，代码一次性 |
| 有界 Bounded | 改动**本仓库里已存在的**流程，小改动 | 对话里的简短设计 + 批准 |
| **架构级 Architectural** | **新项目、新子系统** | 完整流程：提问→方案→分节设计→书面规格 |

本项目是**全新项目**，明确走**架构级**路径。模型应当**明确说出**这个判断：

> "这是新项目，属于架构级任务，我会走完整流程：先澄清问题，再给 2-3 个方案对比，然后分节给设计，最后落一份设计文档。"

#### 流程要点

1. **探索项目上下文**：读现有仓库、文档、最近提交
2. **逐个提澄清问题**：每次只问一个，问到能定方案为止
3. **给 2-3 个方案 + 权衡 + 推荐**（不是直接给一个答案）
4. **分节展示设计**，每节获得批准再继续
5. **写设计文档**：`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
6. **规格自检**：查占位符、矛盾、模糊处、范围是否失控
7. **请用户审查规格文件**
8. **转交 `writing-plans`**

#### 本项目的方案比选示例

技能会让你在两个可落地的架构之间做选择，而不是空谈：

**方案 A：单体 + 语义匹配服务（推荐给首期）**

| 维度 | 说明 |
| --- | --- |
| 架构 | FastAPI 单体 + PostgreSQL + pgvector |
| 匹配 | 技能名片存向量，双向量相似度召回，规则重排（年级/院系/信用分） |
| 优点 | 3 个月能上线；运维简单；无跨服务事务 |
| 缺点 | 匹配算法调整需发版 |

**方案 B：微服务 + 独立推荐引擎**

| 维度 | 说明 |
| --- | --- |
| 架构 | 用户服务 / 匹配服务 / 预约服务 + 消息队列 |
| 优点 | 推荐可独立迭代 |
| 缺点 | 首期成本高；2 万用户量用不上 |

> 推荐 A，理由是**规模不需要**、且首期目标是验证而非承载。这类"推荐 + 理由 + 什么情况下改选"的结构，是 brainstorming 的典型输出。

#### 设计文档应当包含

- **数据模型**：`user`、`skill_card`（会什么/想学什么）、`swap_request`、`appointment`、`review`
- **核心流程**：注册实名 → 建技能名片 → 匹配 → 发起互换 → 预约 → 履约 → 互评
- **接口边界**：哪些是同步 API，哪些异步（向量生成、内容审核）
- **失败与边界**：匹配为空怎么办、爽约如何记录、被拉黑

产出：`docs/superpowers/specs/2026-11-07-skill-swap-app-design.md`

---

### 3.3 第三步：用 `writing-plans` 写实现计划

设计文档批准后，`brainstorming` 会转交 `writing-plans`。它假设**读计划的工程师对项目零上下文**，所以要把一切都写清楚。

**计划存放**：`docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`

#### 计划的关键结构

1. **文件结构先行**：在拆任务之前，先列出要创建/修改的文件及各自职责
2. **任务粒度**：一个任务是"能独立承载一轮测试循环、且值得一个新审查者把关"的最小单元
3. **每任务含**：要改哪些文件、代码要点、测试怎么写、怎么验证
4. **禁止占位符**：不许出现"TODO"、"类似上文"、"稍后补充"

#### 本项目的任务拆分示例

| # | 任务 | 交付物 | 可独立测试 |
| --- | --- | --- | --- |
| 1 | 项目骨架 + 配置 | 可启动的空服务 + `/health` | ✓ |
| 2 | 用户与实名认证 | 注册/登录/实名校验 | ✓ |
| 3 | 技能名片 CRUD | 建卡、改卡、查卡 | ✓ |
| 4 | 名片结构化（LLM 补全标签） | 输入"会修电脑"→ 结构化标签 | ✓ |
| 5 | 向量生成与入库 | 名片变更异步生成 embedding | ✓ |
| 6 | 双向匹配接口 | 给定用户 → Top-N 候选 + 理由 | ✓ |
| 7 | 互换请求与状态机 | 发起/接受/拒绝/过期 | ✓ |
| 8 | 预约与履约 | 约时间地点、完成确认、爽约记录 | ✓ |
| 9 | 互评与信用分 | 评价、聚合、影响排序权重 | ✓ |

注意任务 2-9 都以**可独立测试的交付物**结束——这是技能强制的，避免出现"写了三个任务才能测一次"的计划。

---

### 3.4 第四步：执行与验证

#### 执行

计划批准后，用 `executing-plans`（或需要并行时用 `subagent-driven-development`）按任务推进，每个任务后设审查检查点。

#### 编码纪律：`test-driven-development`

每个任务都走 **红 → 绿 → 重构**：

```text
1. 写一个失败的测试（红）
2. 写刚好让它通过的实现（绿）
3. 在测试保护下重构
```

以任务 6（匹配接口）为例，先写测试：**给定用户 A（会摄影/想学吉他），应返回至少 1 个"会吉他且想学摄影"的候选**——先让它失败，再实现。

#### 出错时：`systematic-debugging`

禁止"试一下改这里看看"。流程是：**先定位根因，再提出修复**。例如"匹配结果为空"时，要依次验证是向量没生成、召回阈值过高、还是过滤条件把它排除了。

#### 收尾：`verification-before-completion`

在说"做完了"之前，**必须实际运行**验证命令并展示输出：

```bash
pytest tests/ -v
uv run uvicorn start:app --reload   # 手动确认关键接口
```

技能明确要求：**没有命令输出，就不许声称完成**。

---

### 3.5 这个范例里技能是怎么串起来的

| 顺序 | 技能 | 输入 | 输出 |
| --- | --- | --- | --- |
| 1 | `requirement-analysis` | 一句话想法 | PRD + 用户故事 + 优先级矩阵 |
| 2 | `brainstorming` | PRD | 方案比选 + 设计文档 + 规格 |
| 3 | `writing-plans` | 设计文档 | 9 个可独立测试的任务 |
| 4 | `executing-plans` | 计划 | 逐任务实现 + 审查点 |
| 5 | `test-driven-development` | 每个任务 | 带测试的代码 |
| 6 | `systematic-debugging` | 失败现象 | 根因 + 修复 |
| 7 | `verification-before-completion` | 完成声明 | 实际验证输出 |

**注意**：第 1、2 步**不写业务代码**。这是最容易被跳过的部分，也是 superpowers 最想守住的地方——需求没定清就写代码，返工成本最高。

## 4. 可选增强：把需求变成能点的原型

如果评审需求时，对方看不懂文字 PRD，可以加一步 `prd-html`：把 PRD 转成可点击的多页面 HTML 原型。

它的核心是「MD 是唯一事实源，HTML 是派生产物」，并且会在 `spec/` 下建三件套：

| 文件 | 作用 |
| --- | --- |
| `spec/_导航地图.md` | 页面清单 + 跳转关系 + 优先级 |
| `spec/_公共规范.md` | 项目级 design token |
| `spec/XX-页面名.md` | 每页规格 |

纯展示型页面也可以用 `common-website-design` 生成框架无关的静态设计原型（8 种页面原型 × 9 套设计包）。

> 注意：这两个技能产出的是**设计原型**，不是可上线的业务系统，与第 3 节的开发链路是并列关系，不是替代关系。

## 5. 常见问题

### Q1：技能没被触发怎么办

`description` 决定触发。如果模型没自动用上，就**点名**："请使用 brainstorming 技能"。也可以让它先说明打算用哪个技能、为什么。

### Q2：能不能直接跳到写代码

技术上可以，但你会失去三样东西：需求澄清帮你避开的返工、方案比选帮你避开的架构坑、以及验收标准帮你定义的"什么叫做完"。superpowers 的定位就是**把你按在流程上**。

### Q3：小改动也要走完整流程吗

不用。`brainstorming` 的三条路径里，**有界（Bounded）**任务只需在对话里给一份简短设计并拿到批准，不写规格文档。判据是"**要改的那条流程此刻就在仓库里、可以读吗**"——能读，就是有界。

### Q4：装了这么多技能，会不会互相打架

主要风险是**同名技能**。DSH 在同一目录下要求 `name` 唯一。本仓库的做法是：

- `.agents/skills/` 与 `.codebuddy/skills/` 内容完全一致（superpowers-zh 中医版）
- `.dsh/skills/` 只放 DSH 侧要用的，避免与上面重复

如果你新增技能，**先检查 `name` 是否已存在**。

### Q5：会话跑歪了怎么复盘

用 `diagnosing-superpowers`。它会读取会话 transcript，逐条给出**带 `path:line` 证据**的发现，并生成排障报告（而非凭记忆猜测）。产物默认在 `~/.superpowers/diagnosing-superpowers/<session-id>/`。

## 6. 速查：最小上手路径

```text
1. 想清楚要做什么（一句话就够，别先想技术）
        ▼
2. "用需求分析帮我把这个想法梳理成需求"
        ▼
3. "按 brainstorming 走架构级流程，给我 2-3 个方案"
        ▼
4. 审设计文档 → "批准，转 writing-plans"
        ▼
5. 审实现计划 → "开始执行，每个任务后给我看测试"
        ▼
6. 跑验证 → 确认输出 → 才算完成
```
