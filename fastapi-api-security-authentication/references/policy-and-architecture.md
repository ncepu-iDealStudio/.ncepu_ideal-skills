# 认证与授权设计

目标是加固现有 API，防止未授权访问、水平越权和垂直越权；保留原脚手架的 Resource → Service → Repository → Model 分层。原脚手架 Skill 只读。

## 一、确定实际规则

1. 读取项目现有路由、SQL/模型、账号和角色、Service 与测试，列出实际 HTTP 方法、路径、用途、对应角色、对象归属和规则依据。与实际注册路由交叉核对，包括隐藏接口和非 `*Resource.py` 文件中的路由，不能只看 OpenAPI 或文件命名。
2. 用户未提供业务规则也继续执行：按[权限推断与默认策略](default-policy.md)结合现有证据设计角色、对象和字段范围；说明规则来自用户、证据推断还是默认选择。不能将字段名或示例记录单独当成真实归属，也不能因缺少规则说明而对全部角色关闭普通业务。无法安全确认身份或建立对象关系时，限制相关普通用户访问并说明阻碍。
3. 白名单逐项明确 HTTP 方法和路径，例如约定的登录入口；其他业务路由默认受保护。健康、文档、HEAD、OPTIONS/CORS 按实际部署和框架行为分别确认。禁止仅靠前缀、模糊匹配或忽略方法放行；规则缺失或检查失败不得默认允许。

## 二、代码位置与执行

- 沿用脚手架已有的 `middleware/`（不是凭猜测新建相近目录），在其中组织白名单、令牌认证、角色/对象权限判断和供接口使用的**鉴权装饰器**。在应用工厂或现有装配位置接入请求认证；登录等公开入口应有明确公开标记或白名单规则，不能对其施加必须登录的检查。
- 每个受保护接口明确使用该目录定义的鉴权装饰器，检查经过认证的主体及该操作允许的角色；不能仅因为有 `@router.get` 或普通异常装饰器就认为完成。非白名单业务路由漏挂装饰器时，应在启动核对阶段报错，或在请求执行前拒绝，不能只验 JWT 签名后继续执行未声明权限的路由。检查覆盖实际注册路由，白名单是公开接口的明确例外。
- 接口对象权限按已确认的业务关系检查：A 能否访问指定对象须从服务端可信数据判断。对象查询和列表过滤放在 Service 中，必要时由装饰器调用 Service 或由 Service 执行具体归属判断；Resource 不得直接调用 Repository。创建检查目标归属，更新/删除先检查原对象，修改关联时还要检查目标；列表在分页与计数之前过滤。
- 认证得到的用户 ID、角色和状态来自验证后的令牌和可信账号来源；不信任客户端提交的角色、用户 ID 或归属值。不能通过任意字段值碰巧等于用户 ID 推定归属；缺失、重复或不可判断的归属默认拒绝。
- 不允许普通用户通过创建、更新、状态变更等入口修改无权字段（如角色、状态或归属）；分别检查继承字段、显式 `null` 和更改关联的情形。响应不返回密码、密码哈希、密钥或作为普通业务数据的令牌；涉及个人数据或其他敏感字段时按业务规则最小化返回。

### FastAPI 装饰器兼容性

鉴权装饰器需兼容 FastAPI 的参数注入、异步函数和 OpenAPI：使用 `functools.wraps` 保留签名，异步包装器正确 `await`；路由注册装饰器应位于鉴权装饰器外层，确保实际注册的是受保护函数。与项目原有异常处理装饰器共同使用时，认证和授权错误不能被改成 500。针对真实路由验证装饰器顺序、依赖注入、状态码及 OpenAPI，不能以存在装饰器名字代替请求测试。若存在同步接口，需分别正确支持同步和异步。

项目启用 OpenAPI/Swagger 时，声明 Bearer 安全方案并给受保护操作添加相应 `security`，公开登录不要求已有令牌，使文档能够提交认证后的请求。仅 `/openapi.json` 返回 200 不算检查通过；这些声明不能替代实际鉴权。可以用 FastAPI 的认证依赖辅助文档，但受保护接口仍要接入所要求的鉴权装饰器。

## 三、登录和令牌

- 登录入口必须先通过[预检与门禁](preflight-and-gates.md)：无登录或令牌不合格时停止询问，**仅在用户明确同意后**才在原有分层中新增或修订登录。失败统一返回不泄露账号存在性的错误，设置合理的登录失败尝试限制并说明其适用范围，不记录密码、令牌、密钥或其片段。未知历史密码格式不可绕过验证，不擅自重置现有账号；记录兼容或迁移阻碍。脚手架已有 JWT 工具不等于已有登录接口。
- 新密码使用 Argon2id；密码输入、存储和返回遵循安全边界。数据库字段容纳不下哈希时提供必要迁移步骤，按授权范围执行；不能只改临时测试库却交付无法重建的项目。账号准备遵循默认策略中的最小初始化要求，不扩展完整账号管理系统。
- 按 `Authorization: Bearer <token>` 接收 JWT，固定允许的算法并验证签名、过期时间及项目要求的声明。签发、验签和强度检查必须使用同一配置来源；拒绝缺失、默认或弱密钥，配置从受保护环境获取，不写入代码或报告。
- 主体必须映射到唯一、非空的真实账号；令牌验证后按当前可信数据检查账号状态与角色。账号禁用、删除或权限改变的生效方式要与实现和测试一致；无服务端撤销机制时不要声称支持即时注销。
- 未提供或无效令牌通常返回 401；身份有效但角色不足返回 403，按项目防枚举规则也可对无权对象返回 404。统一项目的响应格式，不泄露堆栈、密码或令牌。
- 检查认证接入后的异常响应路径：校验错误只返回必要的安全结构，如字段位置、错误类型和固定文案，不回传原始 `input`、请求体或含原始值的异常上下文；日志也不得记录这些内容。错误可能定位到整个 body，其值是嵌套对象或数组，仅按字段名遮盖 `password` 不够。账号认证和恢复秘密的限制见默认策略，内容访问凭据另按明确权限规则处理，不能因管理员身份就直接返回整行数据。
