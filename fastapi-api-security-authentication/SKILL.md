# FastAPI 接口鉴权加固

## 目标和范围

加固现有接口：阻止未授权访问；阻止同权限用户操作无权访问的他人数据（水平越权）；阻止低权限用户执行高权限操作（垂直越权）。优先适配 `sql-to-fastapi-restfulapi-scaffold` 生成的项目，保留现有接口、启动方式及 Resource → Service → Repository → Model 分层；原脚手架 Skill 只读。只做实现和验证上述目标所需的改动，不扩展为通用安全平台。

使用项目已有的 `middleware/`（若目录名不同则沿用现有约定）组织白名单、令牌认证和鉴权装饰器。受保护业务接口必须显式使用该目录定义的鉴权装饰器；`@router.get` 或异常处理装饰器不算。对象查询、归属判断和列表过滤在 Service；Resource 不直接调用 Repository。实现细节见[权限与结构规范](references/policy-and-architecture.md)。

除非用户明确要求兼容其他协议，使用 `Authorization: Bearer <token>` 与正确配置的 JWT；新口令使用 Argon2id。不硬编码密钥或通用管理员口令。不扩展完整注册、找回密码、SSO 或通用权限平台。不得伪造历史对象归属、重置旧密码或修改未授权数据库。

## 强制门禁（未放行不得进入加固实现）

门禁细则、识别规则与停问话术见[预检与门禁](references/preflight-and-gates.md)。先在目标项目根执行：

```powershell
python "<skill目录>/scripts/preflight_auth.py" "<目标项目根>" -o auth-preflight.json
```

再人工核对脚本可能漏掉的隐藏路由与非 `*Resource.py` 文件。**门禁未通过时：停止改业务鉴权代码，只汇报发现并按下面原话询问，等待用户明确回复。**

### 门禁 1：账号表与登录接口

检查哪些表含账号/密码字段；再检查对应 **Service 是否定义登录方法**，以及 Resource 是否暴露登录 HTTP 接口（脚手架约定：Resource 只调 Service）。

- 没有账号密码表：停止，询问是否需要增加最小账号表并实现登录。
- 有账号表但没有登录接口：停止，询问是否需要帮忙实现相应的登录接口代码。
- 多张账号表或多个登录入口：列出后询问以哪一个为鉴权主体，未选定前不继续。

用户同意实现后，只补登录（含分层与 Token 签发），完成后重新跑门禁 1，再进入门禁 2。用户拒绝则终止本轮加固。

### 门禁 2：登录是否符合令牌鉴权

已有登录接口时，检查是否满足：登录成功签发 JWT（或同等签名令牌）；后续业务接口用 `Authorization: Bearer <token>` 校验签名与过期；主体来自服务端可信数据。仅 Session Cookie、明文回传密码、硬编码 `test-token`、只验签不绑定账号，均不合格。

不满足：停止，询问是否需要帮忙修订这些登录接口。同意则只修订登录/令牌，完成后重新检查门禁 2。拒绝则终止本轮。

### 门禁 3：用户角色

门禁 1、2 通过后再查角色/用户类型（字段、枚举、角色表）。

- **发现不同类型用户**：停止，询问这些角色的权限范围，等待用户补充后再设计对象权限。不要凭空补全教师/CMS 等复杂矩阵。
- **完全没有角色设计**：默认 `user`（普通用户）与 `admin`（管理员），写入权限说明后继续，不必再问。

用户明确规则优先于推断；门禁之外的常规 CRUD 权限仍按[默认策略](references/default-policy.md)，不要为每个接口反复提问。

### 常规白名单（门禁通过后、实现加固前）

分析实际注册路由，按常规方式列出精确到 **HTTP 方法 + 路径** 的公开白名单，禁止前缀模糊匹配。默认公开仅限：

- 已确认的登录接口
- 健康检查（如 `GET /health`）
- 项目已启用的文档（`GET /docs`、`GET /redoc`、`GET /openapi.json`）

注册、验证码、静态资源、webhook 列为「候选公开」，未确认前按受保护处理。其余业务 CRUD 默认受保护。白名单写入目标项目的权限说明，并与后续装饰器一致。

## 工作步骤

1. 确认目标项目路径、启动方式、SQL/模型与测试位置。可用计划功能跟踪，不另建状态系统。跑预检脚本，完成门禁 1 → 2 → 3（含必要停问）。
2. 盘点实际注册路由（含隐藏路由），按上一节设定常规白名单；可选 `route_inventory.py` / `auth-policy.json`，格式见[路由库存](references/policy-format.md)。
3. 在 `middleware/` 实现并注册统一认证、白名单与鉴权装饰器，逐个接入受保护业务接口。主体和角色以服务端数据为准；Service 检查归属、创建目标及可改字段，列表在分页和计数前过滤。无凭证或令牌无效 401，角色不足 403，对象不可见可用 404。
4. 按[测试与验收](references/testing-and-acceptance.md)选代表性接口：真实登录、合法操作、未授权、水平与垂直越权；查库确认被拒写入无副作用。核对全部业务路由已挂保护，不要求补全所有业务测试。原 `Bearer test-token` 用例改为真实登录。
5. 写入型测试默认只打已确认的独立测试库，并核验实际连接的实例/库/归属。无安全测试库则停止写入并报告。不得输出密码、密钥、完整令牌或连接串。汇报门禁结论、白名单、角色来源、改动、启动与测试命令、结果及受阻范围。

风险备忘录与 HTTP 探测脚本按需使用，不能代替门禁和正反测试。

## 验收

不能把登录成功、路由清单或全员 403 当作完成。三项同时成立：全部业务接口已接入保护；代表性接口有合法成功与三类拒绝的真实证据；测试与运行步骤可复现。默认 `user`/`admin` 可以完成本轮，不得写成已还原真实产品全部业务规则。
